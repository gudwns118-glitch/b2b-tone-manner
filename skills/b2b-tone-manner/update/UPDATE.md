# 업데이트 절차

말투는 회사·직무에 따라 조금씩 바뀐다. 아래 경우에 이 절차를 돌린다.

- **정기 업데이트**: 현재 회사 profile의 `last_updated`로부터 `update_every_days`(기본 90일)가 지났을 때
- **이직 직후**: 새 회사 메일이 30통 이상, 문서가 5건 이상 쌓였을 때 (보통 입사 1~2개월)

사용자가 "말투 업데이트", "톤 업데이트 해줘"라고 하면 바로 시작한다. 정기 업데이트 시점이면 작업이 끝난 뒤 한 줄로 제안만 하고, 사용자가 승인해야 시작한다.

## 원칙

- **원본은 읽기만 한다.** 메일·Notion·Drive에서 발송·수정·라벨·삭제·공유를 하지 않는다.
- **원문은 저장소 밖에 둔다.** corpus는 임시 폴더(Claude Code scratchpad 등)에 만들고, 끝나면 삭제를 안내한다. 저장소에는 익명화한 규칙과 숫자만 넣는다.
- **본문을 손으로 옮겨 적거나 요약해 corpus에 넣지 않는다.** 도구 결과 파일을 스크립트로만 처리한다. 사람이 재구성한 본문은 말투 근거가 되지 못한다.
- **반영 전에 사용자 승인을 받는다.** 바뀐 점을 표로 보여주고, 승인받은 것만 파일에 쓴다.

## 1. 메일 수집

1. Gmail 커넥터로 본인이 보낸 1:1 메일을 찾는다.
   - 정기 업데이트: `in:sent after:{last_updated}` / 이직 직후: `in:sent after:{입사일}`
   - `search_threads`는 페이지 이동이 안 될 때가 있으니 **주 단위로 날짜를 쪼개** 검색한다. 요약 뷰의 `messageCount`는 믿을 수 없다.
   - 대량·자동 발송(시퀀스, 뉴스레터, 체험권, 이름만 바꿔 3명 이상에게 보낸 제목)은 제외한다. 받는 사람이 1~3명이고 본인이 직접 쓴 메일만 쓴다.
2. 답장이 오간 스레드(`Re:`)를 `get_thread`로 받는다. 결과가 크면 JSON 파일로 저장되는데, 인용 체인 속 본인 메일까지 한 번에 나와 효율이 높다. 파일마다 추출 스크립트를 돌린다.
   ```
   python -I -X utf8 update/extract.py <json 파일> <corpus 폴더> <기간 이름> <수신자 유형> <상황> <내 이름> <get_thread의 sender 주소>
   ```
   - 내 주소는 `get_thread` 결과의 `sender` 값을 그대로 쓴다. 검색 결과에 보이는 주소와 다를 수 있다(예: 점이 들어간 별칭).
   - 발송 도구(CRM·시퀀스 도구)로 보낸 메일은 `plaintextBody`가 "이미지"뿐이다. 이런 메일이 많으면 `messageFormat: FULL_CONTENT`로 받는다. 스크립트가 htmlBody를 텍스트로 바꾼다.
   - 결과가 파일이 아니라 응답 안에 바로 들어오는 작은 스레드는 건너뛴다(위 원칙).
   - 수신자 유형: customer / institution / partner / vendor / creator / internal / english
   - 상황: reply / quote / contract / schedule / followup / apology / reject / won / lost / first / forward
3. 목표 표본: 정기 업데이트 100통 이상, 이직 직후 30통 이상. 모자라면 숫자 비교는 참고만 하고 정성 관찰 위주로 본다.
4. 수천 통 단위가 필요하면 Gmail 커넥터 대신 Google Takeout으로 "보낸편지함"을 mbox로 받아 스크립트로 처리하는 편이 빠르다.

## 2. 문서 수집

1. Notion: 본인이 만든 페이지(`created_by: me`)와 포트폴리오·프로젝트 DB. Drive: `creator = 'me'`인 Docs·Slides.
2. 회의 transcript, 남이 쓴 템플릿·계약서 법무 문안, 설문 응답 원문은 뺀다.
3. **AI 보조로 쓴 문서는 근거에서 뺀다.** 엠대시, "한 줄 요약 —", 학술 인용, "~의 정수" 같은 흔적이 많으면 대조군으로만 쓴다.
4. 문서마다 `title / source / doc_type / date / audience` 헤더와 `---` 구분선을 단 텍스트로 `<corpus>/docs/<source>/` 아래에 둔다(예: `docs/notion/`, `docs/gdocs/`). `docs/` 바로 아래 파일은 집계되지 않는다.

## 3. 분석

```
python -X utf8 update/analyze.py <corpus 폴더>
```
메일: 표현별 출현 비율, 띄어쓰기, 이모지, 서명, 길이를 출력한다. 스레드당 15통 상한이 걸려 있다.
```
python -X utf8 update/analyze_docs.py <corpus 폴더>/docs
```
문서: 문장 종결(개조식·합니다체·해요체·명사형) 비율을 문서 종류·독자별로 센다. 연결어·기호(→ · ※)는 문서를 직접 읽어 확인한다.

## 4. 비교 — 어디에 반영할지 나눈다

| 바뀐 것 | 반영 위치 |
|---|---|
| 서명·소속 줄·제목 말머리·팀명 | `~/.claude/b2b-tone-manner/companies/<회사>/profile.md` 변수·고정 문구 |
| 제품·업무 명사, 회사 고유 안내 메일 구조, 콜드메일 숫자·첨부, 회사 문서 양식 | `~/.claude/b2b-tone-manner/companies/<회사>/profile.md` 업무 어휘·회사 규칙 |
| 메일의 연결어·어미·띄어쓰기·이모지·길이 | 기준을 넘을 때만 `email/voice.md` 수치·규칙 |
| 문서의 종결·구조·기호·어휘 | 기준을 넘을 때만 `document/voice.md`·`document/types.md` |

**모드 규칙을 고치는 기준**: 비율이 10%p 이상 바뀌었거나, 0회였던 표현이 5% 이상 나오거나, 그 반대일 때. 한 회사에서만 나타나는 변화면 모드 규칙 대신 그 회사 profile의 "회사 규칙"에 둔다(예: 새 회사가 공식적으로 "귀사"를 쓰는 문화).

## 5. 반영

1. 바뀐 점을 `항목 | 기존 | 새 수치 | 반영 위치` 표로 사용자에게 보여주고 승인받는다.
2. 승인된 것만 고친다. 새 예문은 이름·회사·금액·연락처를 `{ }`로 익명화한다.
3. 현재 회사 profile의 `last_updated`를 오늘 날짜로 바꾼다.
4. 모드 규칙 파일(`email/`·`document/`)의 예문에 실명·회사명·고객사명·메일 주소·업종 명사가 남지 않았는지 검사한다. 사람·회사별 값은 레포가 아니라 `~/.claude/b2b-tone-manner/`에 두므로 레포에는 남으면 안 된다.
5. corpus 폴더 경로를 알려주고 삭제를 안내한다.
6. 커밋·push는 사용자가 요청할 때만 한다.
